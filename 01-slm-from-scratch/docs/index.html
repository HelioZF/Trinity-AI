A build-it-yourself field guide

How a small language model is built, one part at a time.

This codex is the growing reference for Trinity-AI, Pillar I — a GPT-2-style model, written from scratch in pure PyTorch, that turns a paper title into a plausible scientific abstract. Each phase is added here after it's understood and built — concepts, the “why”, the code, and live demos.

“Hi” → 72 105 → bytes → merge → tokens → the model

Orientation

The project

The goal is a compact language model that performs conditional text generation: given a paper title, it drafts an abstract. That's expansion, not summarization — a deliberate choice.

Why title → abstract, and not full-paper summarization? Because self-attention cost grows quadratically with sequence length. Summarizing whole papers needs a huge context window, which is infeasible on a single 12 GB RTX 3060. Title → abstract keeps the context small and trainable locally — private, free, and entirely on-device.

Design constraint

The 12 GB GPU is treated as a design parameter, not an afterthought. Model size, vocabulary, batch size, and sequence length are all chosen to fit it — using gradient accumulation and mixed-precision (AMP) training later on.

Method

How this codex works

Two passes over the whole project. Iteration 1 — make it work: learn each phase and get the model training and generating. Iteration 2 — make it clean: refine the code and the writing so any programmer can learn from it. This page is the artifact of that second promise, filled in as we go.

Every phase entry aims to answer four questions, in order: why the part exists, what the theory is, how it's built, and does it work.

Chapters come in two tiers, marked in each eyebrow. “Complete / in progress” chapters document what has actually been built and understood, with the real numbers from this repo. “Field guide” chapters (Phases 3–7) are the road ahead — full theory, figures, build order, and pitfalls, written so the project can be continued without a mentor: study the linked resources, follow the build order, check the “done when”. As each is built, its field guide gets upgraded with the real results.

Phase 1 · complete

Tokenization

Turning text into numbers — and back — with a Byte-Pair Encoding (BPE) tokenizer built from scratch.

A neural network is a math machine: it only operates on numbers. A tokenizer is the bidirectional translator between text and integers. It encodes text into a sequence of integer token IDs (via a vocabulary) so the model can process it, and decodes the model's output IDs back into readable text.

Done when

The round-trip holds — decode(encode(x)) == x for arbitrary text — and the vocabulary is a sensible size that actually compresses the input.

Where the tokenizer lives

The tokenizer is the gate at both ends of the model. Text enters through encode and leaves through decode; everything in between is pure integers. The model core never sees a single character.

The big idea

The model core never sees text — it only ever sees integer token IDs. The tokenizer is the translator standing at both doors.

The tokenizer's responsibilities

  • Train — learn the merges from a corpus, building the vocabulary (once, offline).
  • encode — text → token IDs (the entry gate).
  • decode — token IDs → text (the exit gate).
  • Define the vocabulary size — which sets the model's embedding table and output layer dimensions (both grow linearly with vocab — the Phase-1 tradeoff).

Not its job: embeddings, attention, or learning meaning — those belong to the model. After training, the tokenizer is a fixed, deterministic translator.

Why turn text into numbers?

Symbols mean nothing to a matrix multiply. Every character, word, or sub-word must become an integer the model can look up and learn a vector for. The simplest version — character-level — was used in the makemore exercise (a→1, b→2…). A production tokenizer does the same job on smarter units: subwords.

Unicode, code points, and UTF-8

A code point is the integer Unicode assigns to a character: ord('A') = 65, ord('😀') = 128512. There are ~150,000 of them.

A byte holds one of 256 values, 0–255 (2⁸ = 256 values; counting from 0, the max is 255). A code point like 128512 is far too big for one byte — so code points are encoded into bytes by UTF-8, which uses 1 to 4 bytes per character depending on the code point's magnitude:

CharacterCode pointUTF-8 bytes
A65[65]
é233[195, 169]
😀128512[240, 159, 152, 128]

UTF-8 is chosen over UTF-16/32 for three reasons: it's compact (ASCII stays 1 byte, where the others pad with zero bytes), ASCII-compatible (old text is already valid UTF-8), and it yields a clean byte stream (0–255) — a fixed base alphabet of exactly 256 tokens with no out-of-vocabulary ever. All three encodings cover all of Unicode; the win is efficiency.

The granularity tradeoff

Vocabulary size and sequence length pull in opposite directions. Finer units mean a tiny vocabulary but long sequences; coarser units mean a huge vocabulary but short sequences.

GranularityVocab sizeSequence lengthProblem
Raw bytessmallest (fixed 256)longestsequences far too long
Characterssmalllonglittle meaning per token
Wordslargest (100k+)shortestout-of-vocabulary on unseen words
Subwords (BPE)moderatemoderatethe Goldilocks middle

Subwords keep common words as single tokens and split rare words into pieces — word-like efficiency with no OOV. Two costs scale here, and they matter for a small model on 12 GB: the embedding + output layers grow linearly with vocabulary, while attention grows quadratically with sequence length. Lean toward a moderate vocabulary so the lookup tables don't dominate the parameter budget.

BPE training — learning the merges

Byte-Pair Encoding is greedy and simple. Start from the 256 byte tokens, then repeat: count adjacent pairs, merge the most frequent one into a brand-new token, and record it — until the target vocabulary is reached.

  1. Start: vocab = 256 byte tokens; encode the text to a byte sequence.
  2. Count every adjacent pair.
  3. Pick the winner — the most frequent pair.
  4. Merge: mint a new id (256, 257, …), replace all occurrences, and record the merge in order.
  5. Repeat until vocab_size = 256 + num_merges.

Worked by hand on aaabdaaabac:

RoundWinnerMergeResult
start——aaabdaaabac
1aa (4×)aa → ZZabdZabac
2ab (2×)ab → YZYdZYac
3ZY (2×)ZY → XXdXac

Notice merge 3 (ZY) is built on top of merges 1 and 2. That stacking is why encoding must later replay merges in order — see below.

GPT-2's vocabulary of 50,257 is exactly 256 base bytes + 50,000 merges + 1 special token (<|endoftext|>).

encode / decode — and the one key insight

decode(ids) is a straight lookup: map each id to its bytes, concatenate them, then bytes.decode("utf-8", errors="replace"). The errors="replace" matters — a byte-level model can emit a sequence of bytes that isn't valid UTF-8, and instead of crashing, the invalid part becomes the replacement character �.

encode(text) is the subtle one: convert to bytes, then repeatedly apply the earliest-learned applicable merge — the present pair with the lowest merge index.

The key insight

Training picks merges by frequency. Encoding replays them strictly by order. Why? Because later merges are built on earlier ones (the stacking above), and to reproduce the exact tokenization the model was trained on, the merges must fire in the same order they were created. Train by frequency · encode by order · decode by lookup.

Edge case: encode loops while len(ids) >= 2 — with fewer than two tokens there are no pairs, and taking min over an empty set would raise an error.

The code — function by function

The whole tokenizer is five functions of pure standard-library Python — no dependencies. Each one below carries its description, its source, and a live playground: change the inputs and watch the return value update. This is the implementation in src/tokenizer.py.

get_stats(ids) → dict[(int, int), int]

Count every adjacent pair in a list of token ids, returning a dict that maps each pair (a, b) to how many times it appears. It stays neutral about which pair matters — that's the caller's job — so the same counter serves both train and encode. Runs in O(n).

def get_stats(ids):
    counts = {}
    for p1, p2 in zip(ids, ids[1:]):
        counts[(p1, p2)] = counts.get((p1, p2), 0) + 1
    return counts
Try it — count the pairs

Those are the UTF-8 bytes of “hello”. Try one item (5) or none — it returns {}, no crash.

merge(ids, pair, idx) → list[int]

Replace every occurrence of pair with the single new id idx, scanning left-to-right and never overlapping. Returns a new list — the input is untouched. The while loop steps by 2 on a match (so a consumed element can't be reused). Runs in O(n).

def merge(ids, pair, idx):
    newids, i = [], 0
    while i < len(ids):
        if (i < len(ids) - 1) and (ids[i], ids[i+1]) == pair:
            newids.append(idx); i += 2
        else:
            newids.append(ids[i]); i += 1
    return newids
Try it — replace a pair

Try 6, 6, 6 with pair 6, 6 → [99, 6], not [99, 99] (non-overlapping).

train(text, vocab_size) → (merges, vocab)

Learn a vocabulary from text. Repeatedly counts pairs, merges the most frequent, and records it — until reaching vocab_size. Returns two dicts: merges maps pair → id (for encode) and vocab maps id → bytes (for decode). Runs in O(merges × n).

def train(text, vocab_size):
    assert vocab_size >= 256
    num_merges = vocab_size - 256
    ids = list(text.encode('utf-8'))
    merges = {}
    vocab = {i: bytes([i]) for i in range(256)}
    for i in range(num_merges):
        stats = get_stats(ids)
        pair = max(stats, key=stats.get)      # winner = most frequent
        idx = 256 + i
        ids = merge(ids, pair, idx)
        merges[pair] = idx                     # recorded in order
        vocab[idx] = vocab[pair[0]] + vocab[pair[1]]  # cumulative bytes
    return merges, vocab
Try it — learn a vocabulary

Ask for more merges than the text can supply and it simply stops early — the vocab ends up smaller.

encode(text, merges) → list[int]

Turn text into token ids. Convert to UTF-8 bytes, then repeatedly apply the earliest-learned applicable merge (lowest merge index) until none apply — replaying the merges in training order. Runs in up to O(merges × n).

def encode(text, merges):
    ids = list(text.encode('utf-8'))
    while len(ids) >= 2:
        stats = get_stats(ids)
        pair = min(stats, key=lambda p: merges.get(p, float('inf')))
        if pair not in merges:
            break
        ids = merge(ids, pair, merges[pair])
    return ids
Try it — apply learned merges to new text

Trained on a fixed corpus (“the tokenizer turns text into tokens…”, 30 merges). Unseen words still encode — byte-level BPE has no OOV.

decode(ids, vocab) → str

Turn token ids back into text. Look up each id's bytes in vocab, concatenate them, then decode as UTF-8 with errors="replace" — invalid byte sequences become � instead of crashing. A pure lookup: no ordering, no merging. Runs in O(n).

def decode(ids, vocab):
    tokens = b"".join(vocab[idx] for idx in ids)
    return tokens.decode('utf-8', errors='replace')
Try it — bytes back to text (base vocab, ids 0–255)

Try 240, 159, 152, 128 (one emoji = 4 bytes → 😀) or a lone 128 (invalid UTF-8 → �).

Why LLMs act weird — it's often the tokenizer

Many famous failures aren't the model being unintelligent; they're artifacts of tokenization:

SymptomTokenizer cause
Bad spelling / reversing wordsletters are hidden inside multi-char tokens, so the model can't see them
Weak arithmeticnumbers split inconsistently (677 vs 6+77)
Worse in other languagesmore tokens per word → less efficient, less effective training
“SolidGoldMagikarp” glitchesrare tokens that got an id but were barely trained → unstable embeddings

Real GPT tokenizers also add a regex pre-split (so merges never cross letter/number/ punctuation boundaries) and special tokens like <|endoftext|>, inserted outside the merge process. Libraries: tiktoken (bytes-first, inference-only) vs SentencePiece (code-points-first, can train).

Iteration 2 · make it clean

The Tokenizer class

The five functions work — but merges and vocab have to be handed to every call (encode(text, merges), decode(ids, vocab)). They're always born together and used together: a textbook sign that the data and the behaviour that operates on it belong in one object. Wrapping them in a class bundles that state — and unlocks saving a trained tokenizer to disk.

The API, before → after

Before: m, v = train(text, 500); ids = encode(text, m); s = decode(ids, v)
After: tok = Tokenizer(); tok.train(text, 500); ids = tok.encode(text); s = tok.decode(ids)
The caller never juggles merges/vocab again — they live on self.

class Tokenizer:
    def __init__(self):
        self.merges = {}                                  # (pair) -> id   (for encode)
        self.vocab  = {i: bytes([i]) for i in range(256)}  # id -> bytes (for decode)

    def train(self, text, vocab_size): ...   # stores self.merges / self.vocab
    def encode(self, text): ...              # uses self.merges
    def decode(self, ids): ...               # uses self.vocab
    def save(self, path): ...                # write the merges   -> .model
    def load(self, path): ...                # rebuild merges + vocab
    def save_vocab(self, path): ...          # human-readable dump -> .vocab

Saving: store only what you can't rebuild

The .model file stores only the merges — one pair per line, in order — because vocab is fully derivable from them. Even the token id isn't written: the line's position is the id (line 0 → 256). Never persist what you can reconstruct.

.model — exact · loadable.vocab — human · inspection-only
104 101

…		 [ to][k] -> [ tok] 259
[ tok][e] -> [ toke] 260
[ toke][ns] -> [ tokens] 271

The two-file pattern

Real tokenizers write two files from the same state. The .model is minimal and exact — it round-trips, so load reads it. The .vocab renders each token to printable text (control bytes escaped, invalid UTF-8 → �) so a human can read the merge lineage — but that rendering is lossy, so it can't be loaded back. One file for the machine, one for the eyes.

Verified: train → save → a fresh Tokenizer().load(...) reproduces identical merges/vocab and encodes/decodes the same — the tokenizer survives a restart.

Datasets, batches, and why we shuffle

Dataset and DataLoader split one job in two. The Dataset is the data itself: it knows how many examples exist and how to hand over example i. The DataLoader is how the data is delivered: it shuffles, groups examples into batches, and feeds the training loop.

DatasetDataLoader

train / validation split

Held-out examples are set aside before training. Training loss measures memorization; validation loss — on papers the model has never seen — measures learning. When training loss keeps falling while validation loss rises, the model is overfitting: memorizing its textbook instead of learning the subject.

The same discipline validated our tokenizer: the vocab experiment measured compression on held-out abstracts, never on the training sample.

batching — a three-way tradeoff

Examples are processed in batches (groups) rather than one-by-one or all-at-once:

batch sizeVRAMGPU throughputgradient quality
too small (1)trivialGPU starved — parallelism wastedvery noisy steps
middlefits 12 GBGPU saturateduseful noise — helps generalize
too large💥 CUDA OOMfast per stepsmooth but each step over-committed

On a 12 GB card, batch size (with sequence length) is the main knob we turn when memory runs out — it's a design parameter, revisited for real in Phase 5.

shuffling — unbiased batches

Our arXiv file is date-ordered. Without shuffling, every batch would be a slice of one era — “all 2020 papers”, then “all 2021 papers” — so each gradient step would push the model toward one neighborhood of the data, and early epochs would be biased. Shuffling every epoch makes each batch a fair random sample of the whole corpus:

without shuffle: [P1 P2 P3 P4] [P5 P6 P7 P8] … ← neighbors in time, biased with shuffle: [P1402 P88 P3 P957] [P16 P731 …] … ← fair samples of the corpus

Getting the data: commit the recipe, not the data

The pairs come from the arXiv API (scraping is off-limits; pre-made dumps are heavy). The API returns Atom XML; a real parser (never regex-on-XML) extracts <id>, <title>, <summary>, and a clean() pass normalizes whitespace. Requests are paginated and rate-limited (~3 s between calls — API etiquette).

The interesting problem is reproducibility across machines: data files are too heavy (and too re-creatable) for git. The pattern:

Idempotency

build_dataset seeds its seen set from the manifest on disk and counts from len(seen) — so target means total, re-runs are no-ops when satisfied (0.001 s, zero network), and appends never duplicate.

Methodology note: before writing the cleaner we measured the dirt — only ~2 of 50 abstracts actually needed whitespace fixes. Measure your data; don't assume it. The cleaner stays (cheap, uniform), but now it's a decision, not a guess.

Choosing the vocabulary size — an experiment, not a guess

Vocab size can't be derived, but it shouldn't be guessed. It's a bounded decision: calculate the hard constraints, measure the tradeoff, then judge inside the measured range.

The nested-merges trick

BPE training is greedy and deterministic, so the merge list is nested: training to vocab 1,024 yields exactly the first 768 merges of a 4,096 run. Train once at the biggest candidate, then truncate — merges[:v−256] — to simulate every smaller vocab for free.

One 121-second training run on a 400-abstract sample, evaluated on 30 held-out abstracts:

Three signals, one decision: compression keeps climbing, but vocab used collapses (late merges live in the frequency long tail — tokens that exist but rarely fire become undertrained “SolidGoldMagikarp” embeddings), while shorter sequences pay off quadratically in attention.

The decision

vocab_size = 2,048 — trades 2× (still small) lookup params and 79% liveness for a 38% attention discount on every future training step. And it's reversible: nested merges mean vocab 1,024 is literally merges[:768], a truncation away. The final tokenizer was then trained on the full corpus (titles + abstracts, 365 s) and committed as models/arxiv_2048.model — machines must share identical ids.

Special tokens & the anatomy of a training example

The model needs two signals no text can provide: “the title has ended — write the abstract” and “the abstract is finished — stop.” These are special tokens: <|sep|> (id 2048) and <|endoftext|> (id 2049). They are appointed, not learned — BPE's merge loop never creates them; we reserve the next free ids above the trained vocab. Model vocabulary: 2,048 BPE + 2 specials = 2,050 (the GPT-2 pattern: 50,256 + 1 = 50,257).

Unforgeable boundaries

If the literal text "<|sep|>" is encoded, BPE sees only its bytes — 60 124 115 101 112 124 62 — and emits ordinary ids that spell it out. Id 2048 is unreachable from text: it exists nowhere in the merges, so no document can impersonate a boundary. Specials are injected programmatically, after encoding. (Real tokenizers rely on this same property for safety.) The only tokenizer change needed is on the decode side: register readable vocab entries — vocab[2048] = b"<|sep|>" — after every vocab rebuild (train and load), or decoding model output raises KeyError.

The prepare_data.py script applies the recipe to all 2,000 pairs once, writing data/tokenized_cs_LG.jsonl — encode is O(m×n), so we precompute instead of re-encoding every training run. Its length stats (especially max) size the Phase 3 context window.

Measured: 2,000 sequences in 144 s — avg 317 · max 769 · min 51 tokens. That 769 outlier against a 317 average is a classic long tail: the context-window call (truncate the tail vs pay n² for it) is made at Phase 3, with percentiles in hand.

Positional embeddings — attention is order-blind

Self-attention treats its input as a set: shuffle the tokens and the attention scores shuffle with them — nothing in the math knows token 3 comes after token 2. So position must be injected: a second learnable table [context × d_model], one row per position, added to the token embedding. Token identity + location, in one vector.

Self-attention — every token asks questions

Each token's vector emits three projections: a Query (“what am I looking for?”), a Key (“what do I contain?”), and a Value (“what will I hand over if you attend to me?”). Token i's attention to token j is the match between q_i and k_j:

attention(Q, K, V) = softmax( Q·Kᵀ / √d_k  +  causal_mask ) · V

shapes:  [B,T,384] → Q,K,V [B,6,T,64] → scores [B,6,T,T] → out [B,T,384]

Two details carry the magic:

  • ÷ √d_k — dot products of 64-dim vectors grow with dimension; unscaled, softmax saturates into a one-hot and gradients die. Dividing by √64 = 8 keeps the scores in a healthy range.
  • The causal mask — this is a generator: position i may only attend to positions ≤ i. Future scores are set to −∞ before softmax (→ probability 0):
query ↓ · key →Themodellearnsfast
The✓−∞−∞−∞
model✓✓−∞−∞
learns✓✓✓−∞
fast✓✓✓✓

The [T, T] score matrix is the n² object from Phase 2's vocab decision — here it is, in the flesh. 🔁

Multi-head: instead of one 384-dim attention, run 6 parallel heads of 64 dims, each free to learn a different kind of looking (syntax neighbors, long-range topic words, …), then concatenate and project back to 384.

Feed-forward, residuals, LayerNorm

Attention mixes across tokens; the FFN thinks per token — a two-layer MLP applied at every position: 384 → 1536 → 384 with a GELU in between (the classic 4× expansion). Residual connections (x = x + sublayer(x)) make each block a refinement of the identity — the gradient superhighway that lets deep stacks train at all. LayerNorm re-centers each token's vector before every sublayer (pre-norm, GPT-2 style), keeping activations stable.

🔨 Build order — verify shapes at every step

1) one attention head on a toy tensor → 2) add the causal mask (check: upper triangle is −∞) → 3) multi-head + output projection → 4) FFN → 5) one block with pre-norm + residuals → 6) stack 6 blocks → 7) embeddings (token + positional) → 8) final LN + head. Assert the expected shape after every module — shape bugs are 90% of transformer bugs.

⚠️ Pitfalls

A forgotten mask doesn't crash — it cheats. Training loss looks miraculously good (the model peeks at the answer) and generation is garbage. If val loss seems too good to be true, check the mask first. Also: softmax over the wrong dimension, and forgetting √d_k, both train — badly.

Done when

A forward pass on a real batch returns logits of shape [B, T, 2050], and the parameter count printed by a quick loop over model.parameters() lands near ~12 M.

Phase 4 · field guide — not yet built

Training loop

Teach the transformer to predict the next token — and prove the wiring works by making it memorize a tiny batch first.

📚 Study first

The training half of Let's build GPT; for optimizer depth, Karpathy's earlier makemore parts (backprop intuition carries the load).

The objective: cross-entropy on the next token

At every position the model outputs logits over 2,050 tokens; the target is simply the token that actually came next. Cross-entropy = −log p(target), averaged over positions:

lossp(correct token)meaning
7.631/2050 ≈ 0.05%ln(2050) — the untrained baseline. Your very first loss should land here; if not, there's a bug.
3.0≈ 5%learning real structure
1.0≈ 37%strong (on this task, suspiciously strong — check for leaks)

The input/target shift — one sequence teaches T lessons in parallel:

sequence: [ 318 42 901 77 2049 ] inputs x: [ 318 42 901 77 ] ← ids[:-1] targets y: [ 42 901 77 2049 ] ← ids[1:] (each position predicts its right neighbor)

AdamW and the learning-rate schedule

AdamW keeps a per-parameter memory of gradient direction (momentum) and magnitude (variance), adapting each parameter's effective step — with weight decay applied decoupled from the gradient (the W). Starting knobs that work: lr ≈ 3e-4, weight_decay 0.1, default betas. Schedule: a short warmup (Adam's statistics are noise at step 0) then cosine decay.

The loop itself

for step in range(max_steps):
    x, y = next_batch(train_loader)            # [B,T] ids, [B,T] shifted targets
    logits = model(x)                          # [B,T,2050]
    loss = cross_entropy(logits, y)            # ignore_index for padding!
    optimizer.zero_grad()
    loss.backward()                            # 🔁 micrograd, at industrial scale
    optimizer.step()
    if step % eval_every == 0:
        validate()                             # model.eval() + torch.no_grad()
        save_checkpoint(model, optimizer, step)
The golden sanity check

Before any real run: overfit ONE tiny batch. Loop the same 4 examples until loss → ~0. A network that cannot memorize 4 examples has broken wiring — find the bug now, not after an hour of training. Only then train on real data and watch train and validation loss together (🔁 overfitting, Phase 2).

⚠️ Pitfalls

Forgetting optimizer.zero_grad() (gradients accumulate silently); validating without torch.no_grad() (VRAM balloons); computing loss on padding tokens (use ignore_index); leaving the DataLoader unshuffled.

Done when

Loss goes down on a small sample — first to ~0 on the tiny batch (memorization), then meaningfully below the 7.63 baseline on real data.

VRAM engineering

The three techniques

techniquewhat it doescost
Mixed precision (AMP)run activations/matmuls in 16-bit (≈ half the activation memory, tensor-core speed); keep master weights fp32; scale the loss if fp16nearly free — the default ON
Gradient accumulationsimulate a big batch: run K micro-batches, loss/K, backward() each, step() once — effective batch = micro × Ktime, not memory
Gradient checkpointingdon't store mid-block activations; recompute them during backward~30% slower for a big memory win
⚠️ The OOM debugging ladder

When CUDA out of memory hits, climb in order: ① halve the batch → ② gradient accumulation to restore the effective batch → ③ AMP if not already on → ④ shorten the context → ⑤ checkpointing → ⑥ shrink the model. Watch torch.cuda.memory_allocated() to see which knob actually moved the needle — 🔁 measure, don't assume.

Phase 6 · field guide — not yet built

Evaluation & sampling

Quality is meaningless until measured — perplexity for fluency, ROUGE for content, and sampling strategies for generation itself.

Perplexity — fluency, in one number

perplexity = e^(average cross-entropy on the validation set) — intuitively, “among how many tokens is the model effectively guessing?” Computed with model.eval() + torch.no_grad(), never on training data:

val lossperplexityreading
7.632,050random — guessing the whole vocab
4.0≈ 55real structure learned
2.5≈ 12strong for a 12 M model on 2,000 papers

ROUGE — did it write about the right things?

Generate an abstract from a validation title, compare n-gram overlap with the real abstract: ROUGE-1 (words), ROUGE-2 (bigrams), ROUGE-L (longest common subsequence). It's a rough content proxy — treat it as a signal, not a verdict; read the generations too.

Sampling — how the model actually speaks

Greedy argmax loops and repeats. Real generation samples from the distribution, shaped by:

  • Temperature — divide logits by T before softmax. T→0: argmax. T=1: honest. T>1: chaos.
  • Top-k — keep only the k most likely tokens, renormalize, sample.
  • Top-p — keep the smallest set whose cumulative probability ≥ p (adapts k per step).
Sampling lab

A toy next-token distribution after the prompt “machine …”. Drag the temperature; set top-k. Watch probability mass move.

Low T sharpens toward “ learning”; high T flattens toward uniform — even “ banana” gets a chance. Top-k simply cuts the tail before renormalizing.

Done when

Validation perplexity is computed and tracked across checkpoints, and generated abstracts are readable — coherent ML-flavored prose, even if the “facts” are invented (they will be; that's what a 12 M-parameter draft-writer does).

The autoregressive loop

ids = tok.encode(title) + [Tokenizer.SEP_ID]        # the cue: “now write the abstract”
while len(ids) < max_len:
    logits = model(ids[-context:])                  # crop to the context window
    next_id = sample(logits[-1], temperature, top_k)
    if next_id == Tokenizer.EOT_ID: break          # the model says “done”
    ids.append(next_id)
abstract = tok.decode(ids_after_sep)                # text world, re-entered 🔁

One generated token at a time, each fed back as input — the loop is the reason generation is slow, and why real systems cache attention keys/values (the KV cache — an optional optimization here).

title→ encode + <|sep|>→ model · loop until <|endoftext|>→ decode→ draft abstract

The engineer's toolbox

Cross-cutting tools picked up along the way — they apply to every phase.

Big O in sixty seconds

Big O describes how running time grows as input grows — the shape, not the seconds. Constants don't matter: 3n + 7 steps is still O(n). Read it off the code by counting loops:

shapenamedouble the input →in this project
one lookupO(1)same timedict/vocab lookups
one passO(n)2× timeget_stats, merge, decode
a pass per mergeO(m×n)—train, encode (why we precompute!)
all-pairs tableO(n²)4× timeattention (Phase 3)

Worked instance of the n² rule: sequences 500 vs 368 tokens → 500²∕368² ≈ 1.85 — nearly double the attention cost for 36% more length.

Embeddings are weights

A token id is a meaningless label, so each token gets a learnable vector of d_model numbers (we sketch with 384). The embedding table is a matrix of shape [vocab_size × d_model] — one row per token — and it is trained by backprop like any other weight. Looking up row i is mathematically identical to multiplying a one-hot vector by the matrix; the lookup is just the fast shortcut. That's why similar tokens end up with similar vectors: gradient descent pushes them there.

Two independent knobs: vocab_size sets the number of rows (params grow linearly with it); d_model sets the width — chosen separately. Neither changes the other.

Decide like an engineer

Recurring method, worth naming: calculate → measure → judge. Calculate the hard constraints (params, time). Measure the real tradeoff on held-out data (the vocab experiment). Then make a defended judgment inside the bounded range — and prefer reversible decisions (nested merges made vocab size a truncation away). Corollary: measure, don't assume — the data will surprise you (the whitespace that mostly wasn't there; the pip index that swallowed PyPI).

Reference

Glossary

Token
An integer id standing for a chunk of text (a byte, character, or sub-word), looked up in the vocabulary.
Code point
The integer Unicode assigns to a character (e.g. A = 65). Distinct from a byte.
UTF-8
A variable-length encoding (1–4 bytes/char) that turns code points into a byte stream.
BPE
Byte-Pair Encoding — repeatedly merges the most frequent adjacent pair of tokens into a new token.
Merge
A learned rule (a, b) → new_id. Merges are recorded in training order.
Vocabulary
The map from token id to its bytes; its size is a hyperparameter (256 + num_merges).
Round-trip
The correctness property decode(encode(x)) == x.
OOV
Out-of-vocabulary — a unit the tokenizer can't represent. Byte-level BPE never has this.
Special token
An id appointed outside BPE (e.g. <|sep|>=2048, <|endoftext|>=2049) — injected programmatically, unreachable from text, registered decode-side.
Embedding
The learnable vector behind each token id; the table is [vocab × d_model], one row per token, trained like any weight (lookup ≡ one-hot × matrix).
d_model
The width of every embedding/hidden vector — chosen independently of vocab size.
Context window
The maximum sequence length the model accepts; attention cost grows with its square.
Dataset
“The data itself” — knows how many examples exist and how to return example i.
DataLoader
“The delivery” — shuffles the Dataset and serves it in batches to the training loop.
Batch
A group of examples processed in one step — sized to balance VRAM, GPU throughput, and gradient noise.
Epoch
One full pass over the training data; the data is re-shuffled between epochs.
Train/validation split
Held-out examples that measure learning instead of memorization.
Overfitting
Training loss falls while validation loss rises — the model memorizes its textbook.
Manifest
A committed list of exact ids that pins which data a machine should regenerate — commit the recipe, not the data.
Idempotent
Safe to re-run: same command, same end state, no duplicates (e.g. build_dataset, restore_from_manifest).
Compression ratio
Bytes of text per token (higher = shorter sequences); the measurable payoff of a bigger vocab.
Big O
How running time grows with input size — O(1) lookup, O(n) pass, O(n²) all-pairs; constants ignored.
Logits
The raw, unnormalized scores the model outputs — one per vocab token — before softmax.
Softmax
Turns logits into probabilities: exponentiate, then normalize to sum to 1.
Q / K / V
Query (“what am I looking for?”), Key (“what do I contain?”), Value (“what I hand over”) — the three projections behind attention.
Causal mask
Sets future positions to −∞ before softmax so position i only sees ≤ i — what makes the model a generator.
Multi-head attention
Several smaller attentions in parallel (6 × 64 dims here), each learning a different way of looking; concatenated and projected back.
Residual connection
x = x + sublayer(x) — each block refines the identity; the gradient superhighway of deep nets.
LayerNorm
Re-centers/re-scales each token's vector before a sublayer (pre-norm in GPT-2 style) for stable training.
Feed-forward (FFN)
The per-token MLP (384→1536→384, GELU); attention mixes across tokens, the FFN thinks per token.
Cross-entropy
−log p(correct next token) — the training loss; untrained baseline = ln(vocab) ≈ 7.63 for vocab 2,050.
AdamW
Optimizer with per-parameter momentum + variance adaptation and decoupled weight decay.
Checkpoint
Saved model + optimizer + step, so training (or inference) can resume anywhere.
AMP
Automatic Mixed Precision — 16-bit activations/matmuls with fp32 master weights: ~half the activation memory, faster math.
Gradient accumulation
K micro-batch backwards per optimizer step — simulates a K×-larger batch in the same VRAM.
Gradient checkpointing
Drop mid-block activations and recompute them in backward — memory for time.
Perplexity
e^(avg val loss) — “among how many tokens is the model effectively guessing?” Random = vocab size.
ROUGE
N-gram overlap between generated and reference text — a rough content signal, not a verdict.
Temperature / top-k / top-p
Sampling shapers: T scales logits (sharp↔flat); top-k keeps the k best; top-p keeps the smallest set with cumulative probability ≥ p.
Autoregressive
Generate one token, append it, feed everything back, repeat — how GPTs write.
KV cache
Reuse each step's attention Keys/Values instead of recomputing — the standard inference speedup (optional here).
